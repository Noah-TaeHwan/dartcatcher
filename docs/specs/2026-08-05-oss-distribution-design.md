# dartcatcher 오픈소스 배포 설계

작성일: 2026-08-05
상태: 승인됨 (2026-08-05)

## 배경

dartcatcher는 크롤·캡처·OCR 3단계 도커 파이프라인과 공식 OpenDART 교차 검증 모듈로
이루어진 공개 저장소다. 코드와 문서는 갖춰져 있으나 저장소가 "운영되는 오픈소스"로
보이게 하는 장치가 없다. 현재 `.github/` 디렉터리 자체가 없고, CI·릴리스·CHANGELOG·
기여 문서가 전부 빠져 있다. README 뱃지 6개는 모두 shields.io 정적 이미지라 실제로
도는 검사가 하나도 없다.

동시에 포지셔닝 문제가 있다. README는 이 저장소를 "수집 파이프라인"으로 소개하는데,
같은 저장소의 `api/README.md` 는 "259건이 오는 것을 3페이지 긁어 45건 얻는 것과 비교할
이유가 없다"고 적었다. 저장소가 자기 본체를 반박하는 구조다. 실제 가치는 수집 산출물이
아니라 조합 과정에서 나온 세 덩어리에 있다.

1. 기성 이미지가 안 해주는 일을 만났을 때의 우회로 3종 (crawl4ai의 `js_code` 금지,
   Playwright 이미지의 pip 패키지 부재, tesseract 이미지의 한국어 모델 부재)
2. DART에 대한 실측 사실 2건 (화면 목록이 같은 구간의 공시 3건 누락, 259건 중 83건은
   접수번호 앞자리와 `rcept_dt` 불일치)
3. Compose `--exit-code-from` 함정 (두 단계가 실행되지 않았는데 종료 코드 0)

## 목표

저장소를 열어본 사람이 세 가지를 느끼게 한다.

- **돌아간다**: 뱃지가 실제로 무언가를 보증한다
- **닫혀 있다**: 버전이 붙은 지점이 있다
- **받을 준비가 됐다**: 기여 경로가 문서로 있다

## 성공 기준

- CI가 초록불이고, 그 초록불이 검사하는 대상이 명시적으로 존재한다
- README 수치를 하나 고치면 CI가 빨간불이 된다 (실제로 확인한다)
- `v0.1.0` 태그와 GitHub Release가 존재한다
- 저장소 첫 화면에서 네 부류의 방문자가 각자 갈 곳을 3초 안에 찾는다

## 비목표 (범위 밖)

- 단위 테스트 작성
- 영문 README
- 파이프라인 기능 변경, OCR 정확도 개선 (로드맵에 남긴다)
- `data/` 산출물 보관 정책
- 기존 코드 리팩터링

## 결정 사항

브레인스토밍에서 확정한 넷이다.

| 항목 | 결정 |
| --- | --- |
| 대상 독자 | 채용 담당과 기여자 둘 다. 운영 신호를 먼저 세우고 기여 문서를 그 위에 얹는다 |
| CI 내용 | 정적 검사 + 근거 대조. 파이프라인은 CI에서 돌리지 않는다 |
| 릴리스 범위 | `v0.1.0` 태그 + CHANGELOG + GitHub Release |
| 포지셔닝 | 조합 사례집을 본체로 두되 README 상단에 입구 분기표를 넣어 네 부류를 각자 보낸다 |

### CI에서 파이프라인을 돌리지 않는 이유

이미지 합계가 약 14GB고, 무엇보다 CI가 실행될 때마다 DART 서버에 요청을 보내게 된다.
README "크롤링 윤리" 절에 적은 최소 페이지 원칙, 동시 요청 없음과 정면으로 어긋난다.
저장소가 자기 문서를 위반하는 CI를 두는 것은 이 프로젝트의 성격상 받아들일 수 없다.

### 근거 대조를 CI에 넣는 이유

이 저장소의 정체성은 "모든 주장에 근거 파일이 붙어 있다"이다. 아무것도 검사하지 않는
초록 뱃지는 그 정체성과 모순되고, 뱃지가 거짓말이 되는 순간 README의 61.3%도 함께
의심받는다. 검사 대상을 저장소의 강점 자체로 잡으면 뱃지가 장식이 아니라 장치가 된다.

## 접근안 비교 (근거 대조 구현)

| 안 | 방식 | 판정 |
| --- | --- | --- |
| A. 파생형 스크립트 | evidence·data에서 수치를 계산해내고 README에 그 문자열이 있는지 확인 | **채택** |
| B. `claims.json` 매니페스트 | 주장을 JSON에 모으고 검증 | 기각. README 숫자를 사람이 베껴오므로 드리프트가 남는다 |
| C. README 내 HTML 주석 마커 | 주장 옆에 검증 지시를 붙임 | 기각. 우아하지만 주장 5건 규모에 기계장치가 과하다 |

A안의 핵심은 **기대값을 스크립트에 적지 않는 것**이다. 값을 원본에서 계산해내므로
스크립트가 독립적으로 틀릴 여지가 없다. 어느 한쪽만 바뀌어도 검사가 깨진다.

## 컴포넌트 설계

### `tools/check_evidence.py`

**책임**: evidence·data 원본에서 수치를 파생해 README 문자열과 대조한다.
**의존**: 표준 라이브러리만. 네트워크 없음.
**인터페이스**: `python3 tools/check_evidence.py` → exit 0 또는 1.

검사 단위는 `(이름, 파생값, README에 있어야 할 문자열)` 튜플이다.

| 검사 | 파생 방법 | README 대조 문자열 |
| --- | --- | --- |
| OCR 정확도 | `evidence/ocr_quality.txt` 의 `38/62 (61.3%)` 파싱 | `61.3%` |
| HiDPI 정확도 | `evidence/ocr_quality_hidpi_experiment.txt` 파싱 | `83.9%` |
| 캡처 해상도 (main) | PNG IHDR 헤더 직접 읽기 | `1444×2469` |
| 캡처 해상도 (search) | PNG IHDR 헤더 직접 읽기 | `1444×1252` |
| 캡처 크기 (main) | `os.path.getsize` | `410,541` |
| 캡처 크기 (search) | `os.path.getsize` | `226,410` |
| 크롤 건수 | `data/crawl/dart_page*.md` 의 `rcpNo` 링크 수 합계 | `45건` |
| 캡처 파일 수 | `data/captures/*.png` 개수 | `5개씩` |

**에러 처리**: 근거 파일이 없거나 형식이 어긋나면 실패로 끝낸다. "0건 검사 후 통과"를
허용하지 않는다. 검사가 조용히 사라지는 것이 이 장치의 유일한 실패 모드이며, 이는
저장소가 이미 기록해둔 Compose 종료코드 함정과 같은 유형이다.

**출력**: 성공 시 검사 목록을 표로 찍는다. 실패 시 기대값과 실제값을 양쪽 다 보여준다.

### `tools/check_links.py`

**책임**: README 5종의 상대 링크가 실제 파일을 가리키는지, 앵커가 실존 헤딩인지 확인.
**의존**: 표준 라이브러리만.
**주의**: 코드 펜스 내부는 건너뛴다. 루트 README 245~247행의 `(...)` 생략 표기가
오탐으로 잡히기 때문이다.

## 작업 순서

릴리스가 마지막이다. 앞 단계가 초록불이 된 것을 확인하고 태그를 붙인다.

1. PR #4 머지 → main 정리
2. `tools/` 2개 작성, 로컬 통과 확인
3. ruff·shellcheck 로컬 설치 후 실제 실행. 통과 확인. 필요하면 `ruff.toml` 최소 설정
4. `.github/workflows/ci.yml` 작성 → 푸시 후 초록불 확인
5. 기여자 문서 5종 + 이슈/PR 템플릿
6. README 입구 분기표 + CI 뱃지
7. CHANGELOG → `v0.1.0` 태그 → GitHub Release

단계마다 PR을 열지는 않는다. 7단계를 PR 3개로 묶는다. main 직접 커밋은 하지 않는다.

| PR | 포함 단계 | 브랜치 |
| --- | --- | --- |
| (기존 #4) | 1 | `docs/roadmap-api-done` |
| 1 | 2 ~ 4 | `ci/evidence-checks` |
| 2 | 5 ~ 6 | `docs/contributor-guides` |
| 3 | 7 | `chore/release-v0.1.0` |

PR 1을 먼저 머지해 CI가 초록불인 것을 확인한 뒤 PR 2를 연다. PR 2부터는 새 CI가
자기 자신을 검사하게 되므로, README 입구 분기표를 넣는 변경이 근거 대조를 깨뜨리지
않는지 자동으로 확인된다.

## 위험과 대응

| 위험 | 대응 |
| --- | --- |
| ruff가 기존 코드에 다수 걸린다 | 코드를 고치지 않고 `ruff.toml` 로 규칙을 좁힌다. 이번 작업은 리팩터링이 아니다 |
| CI 첫 푸시부터 빨간불 | 3번 단계에서 로컬 실행으로 먼저 확인한 뒤 워크플로를 커밋한다 |
| 근거 대조가 README 서식 변경에 취약 | 대조 문자열을 짧고 안정적인 것으로 고른다 (`61.3%`, `45건`). 문장 전체를 매칭하지 않는다 |
| 검사가 조용히 0건이 된다 | 파일 부재·형식 불일치를 실패로 처리한다 |

## 검증 방법

설계가 실제로 작동했는지 다음으로 확인한다.

- `tools/check_evidence.py` 로컬 실행 → exit 0
- README의 `61.3%` 를 일부러 `62.3%` 로 고쳐 실행 → exit 1, 기대·실제 양쪽 출력 확인
- 고친 것을 되돌린 뒤 재실행 → exit 0
- PR을 하나 열어 CI 3잡이 모두 도는 것을 확인
- 태그 푸시 후 GitHub Release 페이지 확인
