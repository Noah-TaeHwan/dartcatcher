# DART 공식 OpenAPI (교차 검증용)

이 저장소의 본체는 화면을 긁는 파이프라인이다. 이 모듈은 그 파이프라인이 내놓은
결과가 맞는지를 금융감독원 공식 API로 확인한다. 수집 경로를 하나 더 늘리려는
것이 아니라, 크롤링 결과를 채점할 기준을 두려는 것이다.

루트 README의 "공식 API 대안" 절에 적은 주장, 즉 대량 수집이라면 공식 API가
정석이라는 말을 문장으로 두지 않고 실제로 호출해 확인한 기록이기도 하다.

## 인증키 발급

<https://opendart.fss.or.kr> 에서 무료로 발급받는다. 이메일 인증을 거치면
40자리 인증키가 나온다.

키는 환경변수 `API_K_DART` 로만 넘긴다. 저장소 안에는 두지 않는다. `.env` 에도
쓰지 않는데, 이 저장소의 `.env` 는 crawl4ai 토큰 전용이고 키 파일이 하나 늘면
실수로 커밋할 표면도 늘기 때문이다.

```bash
export API_K_DART="발급받은_40자리_인증키"
```

두 스크립트 모두 키를 로그에 찍지 않는다. 요청 주소를 출력할 때 `crtfc_key` 자리는
`***` 로 바꾸고, HTTP 오류가 나도 마스킹한 주소만 남긴다.

## 실행

```bash
python3 api/fetch_disclosures.py          # 오늘(Asia/Seoul) 하루치
python3 api/cross_check.py                # 크롤 결과와 대조
```

날짜를 지정하려면:

```bash
python3 api/fetch_disclosures.py --date 20260805
python3 api/fetch_disclosures.py --bgn-de 20260801 --end-de 20260805
python3 api/cross_check.py --date 20260805
```

표준 라이브러리만 쓰므로 설치할 패키지가 없다. `run_pipeline.sh` 와는 엮여 있지
않고 따로 돈다.

산출물:

| 경로 | 내용 |
| --- | --- |
| `data/api/disclosures_YYYYMMDD.json` | 그날 공시 목록 전체와 요청 메타데이터 |
| `data/api/cross_check_report.json` | 크롤 결과와의 대조 리포트 |
| `evidence/api_fetch_run.txt` | 조회 실행 로그 |
| `evidence/cross_check_run.txt` | 교차 검증 실행 로그 |

### 한 페이지만 받지 않는 이유

`page_count` 상한은 100이고 나머지는 `total_page` 로 나뉘어 온다. 하루치라도
100건을 넘는 날이 흔하다. 2026-08-05는 259건이라 3페이지였다. 첫 페이지만 받으면
그날 공시의 40%가 채 안 되는 양만 손에 들어오고, 크롤 결과와 대조할 때 없는 것을
없다고 잘못 판단하게 된다. 그래서 `total_page` 만큼 순회해 전부 받는다.

전체 목록 조회라 `corp_code` 는 넘기지 않는다. 고유번호 매핑 파일(`corpCode.xml`)을
받을 일도 없다. 대신 `bgn_de` 와 `end_de` 의 간격은 3개월을 넘길 수 없어서 호출
전에 검사하고, 넘으면 기간을 나누라는 메시지와 함께 멈춘다.

## 실측 교차 검증 결과

2026-08-05 기준. 크롤은 10:24 KST에, API 조회는 11:24 KST에 돌렸다. 약 1시간 차이가
난다.

| 항목 | 값 |
| --- | --- |
| 크롤이 얻은 접수번호 | 45건 (3페이지 x 15건) |
| API가 돌려준 당일 공시 | 259건 |
| API에서 확인된 크롤 건 | **45건 / 매칭률 100%** |
| API 응답에 없는 크롤 건 | 0건 |
| 크롤에 없는 API 건 | 214건 |

크롤이 읽어낸 접수번호 45건은 전부 공식 API에도 있었다. 화면에서 긁은 번호가
실재하는 공시라는 것, 접수번호를 잘못 읽지 않았다는 것이 확인된다.

API에만 있는 214건은 성격이 갈린다. `list.json` 응답이 접수 시각 역순으로 오는
것을 실측으로 확인했으므로, 응답 순서를 시간축 삼아 크롤이 훑은 구간의 안팎을
나눴다. 이 정렬은 공식 문서가 보장하는 성질이 아니라 관측된 결과다.

| 분류 | 건수 | 해석 |
| --- | --- | --- |
| 크롤 시점 이후 접수 | 93건 | 크롤이 끝난 뒤 1시간 사이에 올라온 공시 |
| 크롤 범위 밖의 과거 건 | 118건 | 3페이지에서 멈춘 결과. 의도한 제한이다 |
| 크롤 구간 안인데 빠진 건 | 3건 | 아래에 따로 적는다 |

### 구간 안에서 빠진 3건

크롤이 훑은 시간 구간(접수번호 `20260805000118` 부터 `20260805000039` 까지)에
API 기준으로는 48건이 있는데 크롤은 45건만 가져왔다. 빠진 셋은 이렇다.

| 접수번호 | 회사 | 보고서명 |
| --- | --- | --- |
| `20260805000060` | 키움증권 | 일괄신고추가서류(파생결합사채-주가연계파생결합사채) |
| `20260805000055` | 미래에셋증권 | 일괄신고추가서류(파생결합사채-주가연계파생결합사채) |
| `20260805800095` | LS에코에너지 | 연결재무제표기준영업(잠정)실적(공정공시) |

크롤 산출물 `data/crawl/dart_page*.md` 를 직접 검색해도 이 셋은 없고, 세 페이지
모두 표 행이 정확히 15개씩이다. 화면 목록이 이 셋을 빼고 채웠다는 뜻이다.

원인은 확인하지 못했다. 공시통합검색 화면에 걸린 기본 검색 조건이 API의 전체
목록과 다르기 때문으로 보이지만 **미검증**이다. 확실한 것은 화면 목록을 그대로
믿으면 같은 시간대의 공시를 조용히 빠뜨릴 수 있다는 사실이고, 이 3건이 그 증거다.

### 접수번호 앞자리를 날짜로 믿으면 안 된다

당일 259건 중 **83건**은 접수번호 앞 8자리가 `20260804` 인데 `rcept_dt` 는
`20260805` 다. 효력발생안내처럼 전날 계열 번호를 달고 당일 공시로 잡히는
문서들이다. 접수번호에서 날짜를 잘라 쓰는 코드를 짠다면 여기서 어긋난다.
날짜는 `rcept_dt` 필드를 쓴다.

## 요청 한도와 상태코드

인증키 하나당 하루 20,000건까지 호출할 수 있는 것으로 알려져 있다. 다만 이 수치는
`https://opendart.fss.or.kr/intro/main.do` 응답 본문에서 찾지 못해 **공식 문서로는
확인하지 못했다.** 인증키를 발급받은 뒤 이용약관에서 직접 확인하는 편이 낫다.
한도를 넘기면 `status` 가 `020` 으로 온다. 하루치 조회가 3페이지면 3건을 쓰는
셈이라, 이 모듈을 하루 몇 번 돌리는 규모에서 한도에 닿을 일은 없다.

응답의 `status` 가 `000` 이 아니면 `fetch_disclosures.py` 가 상태코드표를 찾아
무엇이 잘못됐는지 적고 종료 코드 1로 끝난다. 처리하는 코드는 다음과 같다.
"실측" 표시가 붙은 것은 실제로 그 응답을 받아 동작을 확인한 코드이고, 나머지는
DART 개발가이드의 상태코드 설명을 옮긴 것이다.

| 코드 | 뜻 | 비고 |
| --- | --- | --- |
| `000` | 정상 | 실측 |
| `010` | 등록되지 않은 키 | 실측. 40자짜리 가짜 키로 호출해 확인했다 |
| `011` | 사용할 수 없는 키 | 일시 중지 상태 |
| `012` | 접근할 수 없는 IP | |
| `013` | 조회된 데이터 없음 | 실측. 2026-01-01로 조회해 확인했다 |
| `014` | 파일이 존재하지 않음 | |
| `020` | 요청 제한 초과 | 하루 한도를 넘겼을 때 |
| `021` | 조회 가능 회사 수 초과 | 최대 100건 |
| `100` | 부적절한 필드 값 | |
| `101` | 부적절한 접근 | |
| `800` | 시스템 점검 | |
| `900` | 정의되지 않은 오류 | |
| `901` | 개인정보 보유기간 만료 키 | |

호출 전에 걸러내는 것도 있다. 키가 없거나 40자가 아닌 경우, 날짜가 `YYYYMMDD`
형식이 아닌 경우, 기간이 3개월을 넘는 경우는 요청을 보내지 않고 멈춘다. 셋 다
실행해서 메시지가 나오는 것을 확인했다. 잘못된 요청을 굳이 보내 한도를 쓰고
`010` 이나 `100` 을 받아보는 것보다 낫다.

## 언제 크롤링이고 언제 API인가

- 공식 API에 있는 항목이면 API를 쓴다. 정기 수집이라면 고민할 것도 없다. JSON을
  그대로 받으니 화면 구조가 바뀌어도 안 깨지고, 한 번 돌려 259건이 오는 것을
  3페이지 긁어 45건 얻는 것과 비교할 이유가 없다.
- 화면에만 있고 API 스펙에 없는 항목이면 크롤링이 남는다. 이미지로 그려진 표,
  스캔 문서, 집계 화면이 여기 해당한다.
- 위 3건처럼 화면과 API가 어긋나는 구간이 실제로 있다. 크롤링 결과를 하류에
  넘길 생각이면 이 모듈 같은 대조 장치를 같이 두는 편이 안전하다.
- 크롤링을 쓰더라도 접수번호처럼 대조 가능한 키가 있으면 API로 채점할 수 있다.
  이 모듈이 하는 일이 그것이다.
